# 系统设计基线与评审门禁

> 2026-10-27 · 草案，尚未冻结。本文明确设计决策和未决问题，不代表固件、硬件、服务或测试已经实现。具体参赛规则和交通规定以发布时有效的官方资料为准。

## 1. 场景与系统边界

首版面向五环内固定门岗的单车道、低速车辆，设备由摄像头、计算模块、4G、音频、供电及外壳组成。它提供提示，不能作为通行许可、违法判定或进京证判断；不连接和控制道闸。地感、继电器和多车道属于未来接口探索，首版不承担门禁控制功能。安装区域、摄像头朝向和出入方向由安装人员确认，不能从车牌推断。

系统逻辑分为采集与识别、规则判断、播报决策、数据更新和运维状态。它们分别输出可追溯的状态；识别失败、资料缺失、播报受抑制和真正的不适用不能合并成一个布尔值。

## 2. 判断与提醒契约

| 判断结果 | 前提 | 默认行为 |
| --- | --- | --- |
| 适用 | 时间、日期、位置、设备可评估的车辆条件及相应规则均已确认，规则匹配；设备无法核验的豁免或车辆类别假设记为 caveat | 若在播报窗口且未被安静时段和去重抑制，发出带核对措辞的提示，不声称违法 |
| 不适用 | 上述依据足以确认所评估的规则不适用，且该规则域覆盖完整 | 保持安静；仅指已覆盖的规则，并不保证车辆可通行 |
| 未知 | 时间、数据、号牌、适用位置、车辆条件、规则域覆盖或车辆豁免条件缺失、冲突或超出范围 | 不输出确定的限行或不限行结论；显示故障状态。车辆相关未知可播放不含车牌的核对提示；数据、时钟、签名等全局故障只亮灯记录，不逐车播报 |

三态描述规则在业务日期内是否适用于该车辆；当前时刻只决定通知类型（当前提醒、预提醒或不播报），不改变适用性。当前状态与当天稍后生效的预提醒分开：例如 06:50 符合当日规则时，播报“今天稍后可能限行，请核对出行时间”，不声称此刻正在限行。预提醒只在限行窗口开始前产生，窗口结束后不补发。安静时段优先于语音；判断结果、播报抑制原因和设备状态分开记录。去重使用单调时钟，冷却从成功开始播报计起，键为“车牌 + 通知类型”；预提醒升级为当前限行允许立即播报，未知提示使用全局冷却。未成功播报不能冒充成功，重启后的行为待设计验证。

只根据蓝牌、绿牌或车牌省份不能确认所有车辆类型、豁免、进京证、方向及路线。影响规则是否成立的条件（如进京证、路线）未确认时为未知；设备无法核验但不改变规则匹配的假设（如本地蓝牌按载客汽车处理）记为 caveat，播报提示核对。外埠载客汽车规则和特殊车辆应单独建模；关于五环外、二环、大兴、顺义及其他区域的限制不在首版判断范围。提醒语不能作“可通行”承诺。

规则以 `Asia/Shanghai` 为业务日期；系统时间失准时不得判断。起止端点应在规则版本中显式定义，按官方解释核验；当前草案中 20:00 终点的包含性尚未确定。当前时间与实际预计经过限行区域的时间不同，提前提示不预测用户后续路线。

## 3. 数据、时间和离线设计

数据发布方与设备是独立信任边界。数据源应保存官方原文链接、发布日期、生效起止、规则适用对象、地域和审阅记录；来源 URL 白名单只能约束位置，不能证明内容真实。采集、解析、人工复核、发布、撤回和修正应留审计记录；解析失败不发布猜测值。HTTPS 校验证书及主机名；镜像也须使用相同可信发布流程。签名、密钥轮换与撤销机制在设计冻结前决策，不能把 HTTPS 当作内容正确性的证明；签名只证明发布方与完整性，不替代人工复核。具体契约见[数据契约 v2](07-data-contract-v2.md)。

设备接受数据至少需要：可信时钟；业务日期匹配；明确有效期且当前时间在有效范围；签名、来源、规则版本、完整性、修订号和规则适用对象通过校验；数据中的时间窗口与区域可供判断且不存在冲突。规则域覆盖不完整时不得给出“不适用”。新旧版本的回滚、未来时间、跨日、截断与未知字段均须显式处理。先完整校验再原子替换持久化缓存；断电时保留上一份完整记录，不能把昨日缓存用于今天。

| 情况 | 设计响应 |
| --- | --- |
| 断网，但当天数据满足全部条件 | 使用当天有效数据，同时提示联网故障 |
| 跨日、过期、规则撤回或仅有旧日数据 | 关键判断为未知；不得按缓存年龄推断可用 |
| 只有轮换表，缺少当日适用日或临时变更依据 | 未知；轮换表本身不证明当天限行 |
| 系统时间不可信 | 关键判断为未知，提示维护；不以系统启动时间猜测日期 |
| 数据内容冲突或无法识别的规则版本 | 拒绝替换，记录原因，结果按有效数据情况确定或未知 |

现有 v1 schema 中 `is_workday` 不是某条限行规则的适用标志，`windows` 可选且没有完整规则语义；不能按它安全实现上述设计。v2 契约设计见[数据契约 v2](07-data-contract-v2.md)：明确规则域、适用对象、时间端点、地区、caveat、覆盖度、修订号、来源、有效期、签名与撤回语义，并要求发布方完成人工复核。本文与 v2 均只提出设计，v1 schema 和样例暂不修改；冻结前需完成 v2 评审、签名密钥方案和发布流程演练。

## 4. 硬件接口和冻结条件

| 接口 | 设计责任 | 冻结前证据 |
| --- | --- | --- |
| 12V 输入及电源 | 独立核算 X5、外设与 LTE 供电；输入最低电压、线损、效率、同时峰值、持续时间和热降额留裕量 | 实际模块版本、负载曲线和适配器能力；接收端实测范围 |
| X5 与载板 | 区分核心板、载板和开发套件；不得把开发套件适配器规格当作核心板功耗 | 官方对应版本引脚、电源、启动、存储、RTC、散热资料 |
| ML307N 电源及控制 | 根据实际子型号确定 VBAT 瞬态、电容、UART 电平、PWRKEY、RESET 和 SIM；定义未上电与背供保护 | 指定型号手册、供电瞬态与接口测量计划 |
| 摄像头与 USB | 确定连接器、电流、ESD、线长和安装方向 | 摄像头供电、图像质量及线缆条件 |
| 音频 | 模组模拟音频与 X5 I2S 为候选；功放桥接输出不得接地或直接并联，切换必须隔离并防止背供 | 实际器件的输入输出、喇叭接线和切换拓扑评审 |
| 天线与机壳 | 天线净空与 50Ω 馈线依据实际天线、叠层和参考平面设计；散热开孔不能自行视为满足 IP54 | 天线布局、机壳防护、散热和测试方法 |

所有信号需在接口表记录方向、电压域、默认态、时序、插拔行为和断电隔离。输入保护、接地和 EMC 应按线缆、回流路径及实际威胁评估；TVS 的存在不等于浪涌或 ESD 已合格。功率与温升值为预算假设，测试极限应取已确认器件与环境约束，不得用相互矛盾的固定跌落阈值替代。

## 5. 隐私与运维

摄像头画面可能包含人脸或环境信息；限制取景范围，不做人脸识别，不在运行中上传或保存原始帧，关闭可能持久化图像的转储或交换路径。默认播报不包含完整车牌，日志优先记录事件类型、原因码、规则版本和系统状态；即使脱敏车牌仍可能关联个人，需限制访问与保留期限。测试数据须有合法来源、明确授权、受控存放与删除计划，公开材料只使用经检查的脱敏资料。

管理接口采用密钥登录、最小权限和无默认密码。配置修改须校验并可恢复；健康状态区分设备运行、数据有效、网络可用及播报故障。诊断或恢复不得泄露车牌、图像、密钥和凭据。

## 6. 验证与设计冻结

| 评审项 | 通过证据 |
| --- | --- |
| 规则与数据 | 按官方来源人工核验版本和日期；v2 签名包、修订号、覆盖度、撤回流程和发布审批通过评审；覆盖调休周末、节假日、临时调整、到期、跨日、未知车辆与时间边界 |
| 信息安全和隐私 | 验证图像、日志、转储、播放与管理路径；记录权限、保留期和数据删除方式 |
| 硬件接口 | 确定实际模块、连接器、电平、上电顺序、音频路径、电源预算与热设计；完成接口评审 |
| 识别与提醒 | 分白天、夜间、逆光、雨天及号牌类别统计；逐车记录漏检、错识、误播和漏播，未知情况单列 |
| 降级恢复 | 设计覆盖断网跨日、时钟回拨、无 RTC、截断/过期/未来数据、断电写入、设备掉线和恢复 |
| 可复现与参赛 | 对照主办方最新规则核验平台资格、开源范围、提交材料及第三方许可 |

验收以车辆通行为统计单位：识别正确率的分母为有效标注车次，误播率的分母为人工标注不应播报的车次，漏播率的分母为人工标注应播报的车次。提前定义标签、异常排除规则及延迟起止，分别报告各场景分母、结果与置信区间；100 车次不足以证明低于 1% 的错误率。200 张白天、100 张夜间只是初步模型评估目标，现场三天/100 车次是可行性观察，不能作为全部指标达标证据。所有阈值在实际测试前评审冻结。
