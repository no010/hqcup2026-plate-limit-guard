# 数据契约 v2 设计审查

> 2026-10-27 · 审查记录；针对 [系统设计基线](06-system-design-baseline.md)、[软件设计](03-software-design.md)和[数据契约 v2 草案](07-data-contract-v2.md)。本记录提出冻结前需解决的问题和建议，不代表草案已批准或功能已经实现。

## 1. 冻结前必须关闭的问题

### R1 · 覆盖声明与车辆条件无法一致表达

v2 的 `coverage.scope` 只有车辆归属和号牌类型，规则却还引用车辆类别、区域和豁免。示例将本地蓝牌声明为 `complete`，同时假定车辆是载客汽车，并承认豁免无法由设备核验；这些条件实际上可能改变规则对具体车辆是否适用。现有字段无法表达“只对已知载客且非豁免车辆完整”，也无法证明不命中时可得出该域不适用。

建议把域覆盖和车辆事实分开建模：覆盖声明限定区域、对象、时间和可评估条件；车辆类别或豁免未知时，**具体车辆的实际适用性为未知**。如需保留便民提示，可单独输出“条件性规则匹配”及核对原因，并明确它不是适用或违法结论。对不命中的尾号，也只能在覆盖完整且相关条件可确定时输出该域不适用；不能从一个域的不适用推导车辆整体可通行。

冻结前需决定 scope 的表达方式、条件性匹配与三态的关系，以及无法识别的车辆类别、豁免、号牌和区域如何处理；原草案中的示例应随最终决定修改，不能作为已通过审查的判断样例。

### R2 · 多规则域缺少合成规则

同一外埠车辆可能同时涉及高峰和尾号规则，现有草案只定义单个域的结果，没有定义多个域如何选择、组合或与通知窗口关联。一个域不适用不能代表其他域不适用，未知域也不能被忽略。

建议先输出各规则域独立的结果、适用区域、窗口和未知原因，再按明确声明的查询范围聚合。对于某一查询范围：有可确认的适用结果时保留该结果并同时列出其他未知域；只有相关域均完整且均不适用时才能得到范围内不适用；其余情况为未知。条件性匹配不升级为确定适用。通知层按当前或即将到来的窗口处理，避免把日级匹配说成此刻限行。具体聚合表需在契约中冻结。

### R3 · 覆盖全天与数据有效期混为一谈

草案要求包的 `valid_from` 不晚于当天零点、`valid_until` 不早于次日零点。若当天中途才有临时通告或需要立即撤回，后发布的包无法准确表达其实际生效区间；也不能保证已签发、离线缓存的包在整天内仍是最新版本。

建议区分：规则或覆盖声称适用的业务时间范围、签名包的可使用时间范围、发布与审批时间。允许包的有效期从日中开始或提前结束，在可使用时间之外返回未知；撤回应从指定时刻生效，并定义离线设备未收到撤回时的残余风险。`generated_at`、审批时间及签发时间的先后关系、时区、端点包含性均需明确；不要把当天较晚签发的内容表述成当天零点已可用。

撤回控制消息的校验也应独立于被撤回规则的有效性：例如原通告过期或被认定无效时，仍需能验证并接收合法的撤回消息；不能先因原规则来源已失效而拒收撤回。

### R4 · 新包拒绝与旧包使用不一致

[v2 草案第 7 节](07-data-contract-v2.md)允许拒绝新包后继续使用仍有效的旧包；[软件设计](03-software-design.md)和[测试计划](04-test-plan.md)中的部分条目则要求一律返回未知。需要明确处理不同故障：

| 事件 | 建议设计方向 |
| --- | --- |
| 新包格式、签名或修订号无效 | 拒绝新包；已有包若仍满足日期、有效期、撤回状态和可信时钟等全部条件，可继续使用，并单独报告更新失败 |
| 没有合格旧包、旧包已失效或日期不匹配 | 未知，不使用旧日包 |
| 已验证的更高版本撤回 | 持久化撤回状态，停止使用该日期的旧包，返回未知 |
| 时钟不可信或持久化状态损坏 | 未知；不得把旧包当作已验证有效 |

这是一项待冻结的建议，需将契约、软件失败模式、测试预期一起更新。签名和最高已见修订号不能证明设备已经收到最新包：网络隔离、镜像停更和设备初始状态都可能让设备继续使用尚在有效期内的旧包，应明确最大可接受滞后、监测和处置策略。

### R5 · 多来源与规则证据关联不足

草案顶层只有一个 `source`，但外埠规则、节假日和临时通告可能来自不同文件、具有不同有效期，而规则中的 `legal_basis` 可以指向其他 URL。仅检查顶层来源的生效期不足以证明每条规则和覆盖声明均有依据。

建议定义来源清单和稳定的来源标识；每条规则、适用日和覆盖声明分别引用其依据，校验各来源及其有效期与对应业务区间的关系。来源有冲突、缺失或被撤销时，受影响的规则域返回未知；一条官方 URL 或页面哈希不替代人工核验。

### R6 · 回滚状态和签名边界需要可验证定义

包、最高已接受修订号和撤回状态必须以同一持久化事务或可验证的原子提交记录更新；需要定义断电前后恢复、高水位损坏、出厂初始化、换机与存储清空的行为，不能静默重置后声称仍有防回滚保护。

草案以 JCS 规范化载荷并签名，但 `envelope_version`、算法和密钥 ID 不在签名字节中。冻结前应规定固定算法与密钥映射、协议域分离和防降级规则；确定是否把安全相关信封元数据纳入签名，并定义密钥撤销、轮换与离线设备的处理。输入解析需明确拒绝重复 JSON 键、非法 UTF-8、超限输入及不符合规范化要求的值，防止不同解析器对同一载荷产生不同解释。

现有示例含占位签名和哈希，不是可验签测试向量。待契约冻结后应设计可复现的规范化字节、密钥、签名及篡改向量，并单独标注测试密钥用途；本文不生成实现或密钥。

## 2. 其他跨文档问题

1. 软件流水线仍有“冷却时间内只处理一次”的表述，可能在规则判断前拦截 06:50 的预提醒到 07:00 当前提醒升级。应分开视觉跟踪去重与通知冷却：识别结果须持续更新，播报决策再按车辆及通知类型限流。
2. 车牌打码后的图片不能验证完整号牌 OCR。测试设计应区分受控、获授权的原始标注集与脱敏的公开报告或示例；原始集的存取权限、保留和销毁必须有记录。
3. v2 规则可能有多个命中，但软件结果只列一个 `rule_id`；应决定返回命中规则集合、各自窗口和原因，避免丢失多窗口信息。
4. 部署位置和行驶路线不是同一事实；安装在五环内的门岗并不能推断车辆后续是否驶入其他受限道路。区域不明确时不能以设备位置替代车辆路线。

## 3. 建议的设计验收用例

以下为设计层测试向量，不是已经执行的测试。期望以本记录建议为准，待决策后再固化到契约与测试计划。

| 用例 | 应验证的结果 |
| --- | --- |
| 本地蓝牌尾号命中，但车辆类别或豁免未知 | 实际适用性未知；可单独形成条件性核对提示，不能声称确定限行 |
| 同一车辆一个域不适用、另一相关域未知 | 合成结果不能为范围内不适用；未知原因可追溯 |
| 假日、临时通告与常规规则分别来自不同来源 | 每个规则及覆盖声明能追溯到有效来源；缺失或冲突影响相应域 |
| 12:00 发布的日中变更或撤回 | 发布前、有效时段内和有效期结束后的行为明确；未接收变更的离线风险单独记录 |
| 无效新包与仍有效旧包并存 | 新包被拒；按冻结后的旧包策略继续或停止判断，并显示更新故障 |
| 已接收高版本撤回后重启、收到旧包 | 撤回状态和最高修订号保持一致；旧包不能恢复当天判断 |
| 包与防回滚状态更新时断电 | 每个断点只恢复完整一致的状态；状态损坏时未知 |
| 多规则窗口及预提醒升级 | 规则集合和各窗口不丢失；视觉跟踪不拦截通知类型升级 |
| 重复 JSON 键、超限数字或非法编码 | 在验签前按明确解析规则拒绝，不因解析器差异得到不同结果 |

## 4. 审查状态

以上为待处理设计问题，尚未修改 v2 schema、固件、发布服务或硬件。签名机制、规则覆盖、车辆假设和发布运维均应在相关责任角色确认后形成一致的冻结版；在此之前，当前 v2 草案及其示例不得作为可直接实施的最终契约。
