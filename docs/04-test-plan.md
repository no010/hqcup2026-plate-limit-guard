# 测试计划：限行哨兵

> 版本：v0.1（草案） · 日期：2026-10-27 · 状态：计划阶段
> 关联文档：[产品规格](01-product-spec.md) · [硬件特性规格](02-hardware-spec.md) · [软件设计](03-software-design.md)
> 下表为计划与目标，不是实测结果；评估口径和新增边界见 [系统设计基线](06-system-design-baseline.md)。

## 1. 测试策略

| 层级 | 目标 | 方式 | 产出 |
| --- | --- | --- | --- |
| 单元测试 | 规则引擎、数据校验、车牌规范化 | pytest，纯函数，无硬件依赖 | 测试报告、覆盖率 |
| 集成测试 | 摄像头 + 识别 + 规则 + 播报 | RDK X5 开发板 + USB 摄像头 + ML307N | 日志、录屏 |
| 系统测试 | 整机电源、接口、散热、断网 | 底板 + 外壳 + 12V 电源 | 测试记录、照片 |
| 现场测试 | 真实门岗、真实车辆 | 连续 3 天，≥100 车次（可行性观察） | 统计表、问题清单 |
| 合规检查 | 开源完整性、许可证、文档 | 人工 checklist | 合规表 |

测试原则：**先测规则，再测识别，最后测整机**。规则引擎是纯函数，必须在没有硬件的情况下先跑通；识别模型和 TTS 可以 mock，避免把硬件问题误判为软件问题。

## 5. 现场测试

**场地**：五环内小区/园区门口，单车道，车辆低速通过。

**样本**：连续 3 天，至少 100 车次，覆盖蓝牌、绿牌、外埠、夜间、雨天。

**记录表**：

| 日期 | 时段 | 车次 | 识别正确 | 误识别 | 应播报 | 实际播报 | 漏播 | 误播 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |  |  |  |  |

**评估口径**：

- 现场 3 天、100 车次只作可行性观察，不作为指标达标证据；所有结果按人工标注车次报告分子、分母和 95% 置信区间。
- 识别率目标为白天 ≥98%、夜间补光 ≥95%，需在更大的标注集上评估；样本量按目标置信区间反推，不能用 100 车次外推。
- 误播率分母为人工标注“不应播报”的车次，漏播率分母为“应播报”的车次。以零误播为例，100 个负样本的 95% 置信上界约 3%，要支持 <1% 的结论需要约 300 个以上负样本或更多。
- 限行判断以人工核对为准；任何确定结论与已核验规则不符都记为缺陷。未知不计入误播，但需单独统计。
- 连续 3 天无系统崩溃是现场稳定性观察，不是 MTBF 证明。
- 所有阈值在测试前评审冻结。

## 6. 大赛验收演示

提交前需要准备：

1. **3 分钟演示视频**：车辆通过 → 识别 → 限行判断 → 语音播报；再演示不限行车辆保持安静；最后演示断网降级。
2. **实物照片**：整机、主板、摄像头、4G 天线、扬声器、安装场景。
3. **测试记录**：识别率、延迟、功耗、温升、现场统计。
4. **开源检查**：仓库包含原理图、PCB、Gerber、BOM、固件、文档；许可证齐全；第三方许可证记录。
5. **复现说明**：BOM、烧录、配置、数据源、已知问题。

演示脚本建议：

| 时间 | 画面 | 说明 |
| --- | --- | --- |
| 0:00–0:30 | 问题与场景 | 北京限行、车主忘记、门口提醒 |
| 0:30–1:10 | 硬件 | RDK X5 底板、ML307N、摄像头、扬声器 |
| 1:10–2:10 | 限行车辆通过 | 识别、判断、播报、日志 |
| 2:10–2:40 | 不限行车辆 | 保持安静，去重生效 |
| 2:40–3:00 | 断网与总结 | 缓存降级、开源地址 |

## 8. 风险与应对

| 风险 | 应对 |
| --- | --- |
| 模型在 RDK X5 上跑不到 5fps | 降帧率、缩小输入、运动触发；必要时换 BPU 模型 |
| 夜间识别率不达标 | 加红外补光、换 WDR 摄像头、调整安装角度 |
| 4G 在门岗信号弱 | 外置天线、延长天线、换运营商；保留 WiFi/以太网 |
| TTS 音质差 | 换 X5 I2S + 本地 TTS；或预录提示音 + 车牌号拼接 |
| PCB 打样延误 | 开发板演示 + 设计文件提交；打样券补打 |
| 现场无法取电 | 12V 适配器从门岗取电；P2 评估 PoE |
