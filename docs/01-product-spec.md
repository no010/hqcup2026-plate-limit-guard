# 产品规格：限行哨兵

> 版本：v0.1（草案） · 日期：2026-10-27 · 状态：规格评审中，未冻结
> 关联文档：[硬件特性规格](02-hardware-spec.md) · [软件设计](03-software-design.md) · [测试计划](04-test-plan.md) · [大赛合规](05-competition-compliance.md)
> 评审补充：[系统设计基线](06-system-design-baseline.md)定义未知状态、提醒语义和设计冻结门禁；本文件所有指标均为待验证目标。

## 1. 背景与目标

北京工作日 07:00–20:00 在五环路以内按车牌尾号限行，尾号每 13 周轮换一次；外埠车辆还有早晚高峰禁入规则。车主忘记当天限行而被处罚的情况很常见。

限行哨兵的目标是做一个**装在门口、不用改变现有道闸、每天自动更新限行信息**的提醒装置：

1. 车辆低速经过门口时识别车牌。
2. 通过 4G 获取当天北京的限行信息。
3. 如适用规则可确认，语音提醒；规则不适用则保持安静，依据不足则提示未知。
4. 断网时仅使用仍适用于当天且可信的数据；条件不足时显示未知状态，提示人工核对。

项目不追求大而全，首版只做“认车牌、判限行、播提醒”三件事。

## 2. 用户与场景

### 2.1 目标用户

| 用户 | 需求 | 关注点 |
| --- | --- | --- |
| 五环内小区/园区车主 | 出门前知道今天是否限行 | 提醒及时、不误报、不打扰 |
| 物业/门岗 | 低成本增加一项便民服务 | 安装简单、不改造道闸、维护少 |
| 参赛评审 | 看到完整的软硬一体开源作品 | 设计完整、可复现、有创新点 |

### 2.2 典型场景

**场景 A：早晨驶出小区**

车主在 2026-10-27（周二）07:10 开车出门，车辆经过门岗摄像头。设备识别到“京A·12345”，当天限行尾号 1 和 6，车辆尾号为 5，不限行，设备保持安静。

**场景 B：限行日出门**

同一位车主在 2026-10-26（周一）06:50 出门。当天限行尾号 5 和 0，车辆尾号为 5。此时尚未进入 07:00 限行窗口，设备只播报“今天稍后可能限行，请核对出行时间”，默认不播完整车牌，也不声称此刻正在限行。车主改乘地铁。

**场景 C：外埠车辆高峰进入**

一辆外埠蓝牌车辆在工作日 08:10 驶向门岗。设备无法确认进京证、车辆类型和后续路线，提示“请核对车辆限行和进京规定”。

**场景 D：断网**

4G 不可用时，设备检查缓存是否适用于当天及其可信程度；无有效数据时进入未知状态并提示人工核对，恢复联网后重新校验。

## 3. 范围

### 3.1 首版范围（MVP）

- 单车道、车辆低速通过（≤20km/h）场景。
- 蓝牌、绿牌、黄牌的车牌检测与字符识别；首版以蓝牌、绿牌为主。
- 京牌蓝牌尾号限行判断；绿牌、黄牌及外埠车辆默认按未知处理，只有规则包明确覆盖且设备可核验时才给出确定结论。
- 每日限行数据通过 4G 自动更新，本地缓存。
- 对适用规则的车辆语音提醒；同一车牌同一通知类型去重。
- 本地日志、状态灯、配置文件的导入与修改。
- 12V 单电源供电，自研 RDK X5 底板。

### 3.2 首版不做

- 不控制道闸、不输出开闸信号（安全责任与场景差异太大）。
- 不做人脸识别、不做人员管理、不做停车计费。
- 不做云端大屏、不做多设备集中管理。
- 不做执法取证，不保存车辆照片。
- 不判断进京证是否有效（设备无法获取该数据）。
- 不覆盖北京以外的城市限行规则（数据结构预留城市字段）。

## 4. 功能需求

| 编号 | 需求 | 优先级 | 可执行验收 |
| --- | --- | --- | --- |
| FR-01 | 车辆经过时完成车牌检测与字符识别，输出车牌号与置信度 | P0 | 200 张测试集：白天识别率 ≥98%，夜间补光 ≥95%；单帧处理 ≤500ms |
| FR-02 | 同一车牌同一通知类型在冷却时间内只播报一次；预提醒升级为当前限行不受限 | P0 | 连续 20 次模拟通过，同类型播报次数 ≤1；升级场景两次都播报；冷却时间可配置，默认 10 分钟 |
| FR-03 | 每天拉取当天 v2 签名规则包，失败重试 | P0 | 00:05 触发，离线则恢复联网后补拉；失败按 1/5/15 分钟重试 3 次，之后每 30 分钟低频重试；日志可见 |
| FR-04 | 按车牌、日期、时间、号牌种类、车辆归属判断是否限行 | P0 | 单元测试覆盖轮换表、字母尾号、节假日、07:00/20:00 边界、外埠高峰 |
| FR-05 | 对适用规则的车辆播报提醒，预提醒与当前限行分文案，默认不播完整车牌 | P0 | 识别到符合提醒条件的车辆后 1.5s 内开始播报；两种文案可区分；播报内容清晰可辨 |
| FR-06 | 断网时按日期与可信性使用缓存，缺失时返回未知 | P1 | 跨日、过期或无有效日规则时不输出确定结论；状态灯与日志提示人工核对 |
| FR-07 | 通过配置文件设置设备位置、提醒窗口、安静时段、音量、数据源 | P1 | 修改配置并重启后生效；非法配置拒绝启动并给出错误日志 |
| FR-08 | 本地日志记录识别结果、判断结果、播报结果，默认脱敏 | P1 | 日志不含完整车牌；不保存图片；保留天数可配置 |
| FR-09 | 电源、系统、4G、故障状态用 LED 指示 | P1 | 每种状态有明确灯语，门岗人员可据此判断设备是否正常 |
| FR-10 | 上电自动启动，异常自动恢复 | P1 | 断电重启后 60s 内进入工作状态；systemd 服务与看门狗生效 |
| FR-11 | 通过网络或 RTC 保持时间准确 | P1 | 联网时 NTP 校准；断电 24h 后 RTC 误差 ≤5s |
| FR-12 | 评估地感/雷达触发、I2C/UART 等扩展接口 | P2 | 设计不影响首版功能，不接入或控制道闸 |

## 6. 关键指标

| 指标 | 目标 | 测量方法 |
| --- | --- | --- |
| 白天车牌识别率 | ≥98% | 200 张实拍测试集，按完全正确计 |
| 夜间补光识别率 | ≥95% | 同一测试集夜间部分 |
| 限行判断准确率 | 确定结论 100% 正确；未知单列 | 规则引擎单元测试 + 人工核对 |
| 误播报率 | <1% | 以人工标注“不应播报”的车次为分母，报告点估计与 95% 置信区间；零误播时约需 300 个负样本才能支持 <1% 上界 |
| 提醒延迟 | ≤1.5s | 从车辆进入画面到扬声器出声，视频计时 |
| 数据有效性 | 判断时使用的数据 100% 适用于当天且在有效期内 | 逐次校验 `business_date`、`valid_from`、`valid_until` 与时钟可信性；无有效数据时输出未知，不以数据年龄推断可用 |
| 离线状态 | 有效当天数据可继续判断；否则明确未知 | 跨日和断网测试 |
| 整机功耗 | 典型 ≤20W | 功率计记录 1 小时 |
| 整机成本 | ≤¥500（不含模块） | BOM 核算 |

识别率与误播率的样本量应按 95% 置信区间反推；表中的 200 张、300 个负样本等数字只是初步评估口径，不能直接当作达标证据。

## 7. 北京限行规则矩阵

下表仅是已知条件下的规则轮廓，并非完整判断表；车辆类别、豁免、证件和具体区域等条件须另行核验。最终以北京市人民政府和交管部门发布的通告为准。

| 车辆类型 | 工作日 07:00–09:00 | 工作日 09:00–17:00 | 工作日 17:00–20:00 | 其他时段 |
| --- | --- | --- | --- | --- |
| 京牌蓝牌（适用尾号规则且非豁免车辆） | 尾号限行，五环内（不含五环） | 同左 | 同左 | 所述尾号规则不适用 |
| 外埠载客汽车（相关条件已确认） | 高峰限制，五环内（含五环） | 尾号限制，五环内（含五环） | 高峰限制，五环内（含五环） | 其他限制须另行核验 |
| 绿牌新能源 | 号牌颜色不足以证明豁免，默认未知 | 同左 | 同左 | 其他适用限制未知 |

补充规则：

- 尾号为英文字母的按 0 管理。
- 临时号牌按尾号数字限行。
- 对所引用的 2026–2027 本市尾号规则，因节假日调休上班的周六、周日也不执行该尾号限行；其他规则须分别核验。
- 外埠车辆进京证不在本设备判断范围。
- 安装位置假设为五环内门口；若装在五环外，尾号规则不适用，设备不推断车辆后续路线。

### 7.1 两个时间窗口

设备区分两个窗口，避免“规则上还没到 7 点，但车主已经出门”的漏提醒：

| 窗口 | 默认值 | 用途 |
| --- | --- | --- |
| 限行窗口 | 07:00–20:00 | 决定当前提醒与预提醒的时间；不改变规则的日级适用性。端点是否包含以规则包中的显式标志为准，未核验时不得判断 |
| 提醒窗口 | 06:30–20:30 | 在限行窗口开始前预提醒、在限行窗口内提示当前状态；提前提醒不得声称当前正在限行 |

预提醒只向前看：仅在限行窗口开始前且处于配置的提前量内产生，窗口结束后不补发。默认提前量为 30 分钟。提醒窗口、安静时段、安装区域和提前量都通过配置文件调整。

## 8. 数据与降级策略

### 8.1 数据来源

- 权威来源：北京市人民政府通告、北京市公安局公安交通管理局发布信息。
- 设备数据：由仓库的发布流程生成 v2 签名规则包，设备通过 4G HTTPS 拉取并验签；契约见[数据契约 v2](07-data-contract-v2.md)。v1 的 `data/current.json` 只是示例，不用于判断。
- 备选通道：GitHub raw、jsDelivr CDN、自建镜像；所有通道同等不可信，设备必须验签后才能使用。

### 8.2 数据有效性与覆盖分级

| 数据状态 | 行为 | 状态指示 |
| --- | --- | --- |
| 有效且适用于当天，相关规则域覆盖完整 | 按对应规则判断 | 正常：ERR 灭 |
| 数据有效，但当前车辆所属规则域覆盖不完整 | 该域输出未知，其他完整域不受影响；不播报确定结论 | 降级：ERR 慢闪 |
| 日期不匹配、过期、签名或关键依据缺失 | 结果为未知，不播报确定结论 | 故障：ERR 常亮 |

内置轮换表仅提供指定周期的尾号参考，不能单独证明当日规则有效；节假日、临时调整及车辆豁免等无法确认时返回未知。

## 9. 隐私与安全

- 摄像头图像只在内存中处理，默认不保存、不上传。
- 日志默认只记录脱敏车牌（如 `京A·1***5`）和判断结果。
- 不做人脸识别和人员身份关联；限制摄像头视野并避免保存原始画面。
- 设备外壳贴提示：“本设备仅识别车牌用于限行提醒，不保存车辆图像”。
- 管理入口只开 SSH，使用密钥登录；禁止默认密码。
- 数据拉取使用 HTTPS；签名、密钥轮换与撤销方案在设计冻结前确定，并在首次现场使用前完成实现与验证。HTTPS 只保护传输，不能证明内容真实；规则包校验见[数据契约 v2](07-data-contract-v2.md)。
- 调试用的测试图片必须打码，不得提交真实车主信息到仓库。

## 10. 风险与假设

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| RDK X5 Module 的引脚、存储、RTC 充电要求未最终确认 | 阻塞原理图 | 先下载官方 Module Datasheet、Hardware Design Guide、Pinout 和底板参考设计 |
| ML307N 离线 TTS 的 AT 指令与音频输出未验证 | 音频方案可能返工 | 先做冒烟测试；保留 RDK X5 I2S + MAX98357A 备选路径 |
| 车牌识别模型精度与许可证不确定 | 识别率或开源合规风险 | 选型时核验许可证；先 CPU 方案跑通，再评估 BPU 加速 |
| 限行数据源页面结构变化或访问受限 | 数据不更新 | 多通道 + 当天有效缓存 + 人工复核发布；轮换表只作核对，不能替代当日规则包 |
| GitHub raw 在国内访问不稳定 | 设备拉取失败 | 使用 jsDelivr 或自建镜像；设备按顺序回退，所有镜像都必须验签 |
| 门口没有 12V 电源 | 无法安装 | 支持 12V 适配器；P2 评估 PoE |
| 车牌属于个人信息 | 隐私争议 | 本地处理、不存图、日志脱敏、现场提示 |

## 11. 开放问题

1. RDK X5 Module 是否自带 eMMC？若没有，Micro SD 卡是系统盘，必须选用工业级卡。
2. RDK X5 Module 的 RTC 是否支持可充电纽扣电池？官方参考设计如何使用？
3. ML307N 具体子型号（-DL/-DC/-BL/-GL）由大赛提供哪一款？是否支持离线 TTS？
4. ML307N 的 TTS 是 AT 指令触发还是 OpenCPU API？音频输出是模拟 DAC 还是 PCM？
5. 摄像头选型：门口逆光、夜间车牌反光，是否需要 WDR + 红外补光？
6. 门岗安装位置能否固定 12V 电源与摄像头支架？是否需要 PoE？
7. 大赛最终提交物是否要求指定平台工程页、演示视频时长、PDF 格式？以官方通知为准。
8. 绿牌新能源、临时号牌、外埠车辆的边界规则是否需要首版覆盖？
9. v2 规则数据的签名密钥由谁保管，发布审批与撤回由谁执行？
